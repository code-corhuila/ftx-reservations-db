# ftx-reservations-db

> Reservations domain: schema, lifecycle rules, roles and Flyway migrations

Part of **Futbolix**, the distributed system for reserving the four football courts of a
single sports facility. Governance and documentation live in
[`ftx-docs`](https://github.com/code-corhuila/ftx-docs). User stories: HU-RES-002 (create),
HU-RES-004 (look up), HU-RES-005 (confirm or reject from the payment), HU-RES-006 (outbox),
HU-RES-007 (cancel). Source model: `ftx-docs/06-data/models.md`, service `reservation-service`.

## What this repository is (and what it is not)

Following **Annex J**, Futbolix has **one PostgreSQL instance**, defined in
[`ftx-infra-postgres`](https://github.com/code-corhuila/ftx-infra-postgres). This repository:

| Does | Does not |
|---|---|
| Own the structure of the `reservations` schema: tables, functions, triggers, indexes, roles | Define a database container or a volume |
| Enforce the rules that only the database can guarantee (double booking, lifecycle) | Create login users (that is `ftx-infra-postgres`) |
| Ship the migration runner (`deploy/compose.yml`) | Contain application code (that is `ftx-reservations-api`) |
| Prove in CI that the schema builds from scratch, reverts and builds again | Seed reservations: there is no seed, so no real person is ever stored by a migration |

## Data model

### `reservations.reservation`

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | `pk_reservation` |
| `reservation_code` | `varchar(20)` | Unique (`idx_reservation_reservation_code`), `^[A-Z0-9]{1,20}$`. Generated by the API with `SecureRandom`; it is the customer's secret |
| `customer_name`, `customer_email`, `customer_phone` | `varchar` | Contact data of the anonymous customer |
| `court_id` | `uuid` | Court of the courts domain. **No foreign key** (Annex J.3.4); the API validates it through `ftx-courts-api` |
| `reservation_date`, `start_time`, `end_time` | `date`, `time` | `chk_reservation_time` (end after start) and `chk_reservation_whole_hours` (BR-004) |
| `status` | `varchar(20)` | `PENDING`, `CONFIRMED`, `CANCELLED`, `REJECTED` (CHECK, never ENUM) |
| `amount`, `currency` | `bigint`, `char(3)` | Integer COP (`Money` of `_shared.yaml`), `> 0`, `COP` |
| `cancelled_at`, `cancelled_by`, `cancellation_reason` | | FR-035. `CANCELLED` ⇔ actor and date present |
| `period` | `tsrange` | Generated from date + hours; never written by anyone |

**Double booking (BR-005)** is stopped by the engine, not by code: the exclusion constraint
`reservations_no_double_booking` rejects any `PENDING` or `CONFIRMED` row whose court and
`period` overlap another active row. The losing transaction gets SQLSTATE `23P01`, and the API
answers **409 `RESERVATION_SLOT_UNAVAILABLE`**. `CANCELLED` and `REJECTED` rows free their slot
automatically, with no cleanup job.

**Lifecycle**, enforced by `trg_reservation_guard_transition`:

```
PENDING ──> CONFIRMED ──> CANCELLED
   ├──────> REJECTED
   └──────> CANCELLED
```

`CANCELLED` and `REJECTED` are final. Code, court, slot, amount and email never change after
creation. A `PAID`-like status does not exist: a reservation is `CONFIRMED` only when the API
consumes `PaymentApproved` from the payment provider flow (M8).

### Supporting tables

| Table | Why |
|---|---|
| `idempotency_key` | `POST /reservations` with the same `Idempotency-Key` returns the original reservation. `request_hash` detects the same key with a different body |
| `outbox_event` | Transactional outbox (ADR-006, HU-RES-006): the reservation and its `ReservationCreated` / `ReservationCancelled` are written in one transaction; a relay publishes them to `futbolix.events` |
| `processed_event` | Idempotent consumer: the `eventId` of `PaymentApproved` / `PaymentRejected` is stored with the status change, so a redelivery changes nothing |

### Access (Annex J.7)

| Role | Kind | Can |
|---|---|---|
| `reservations_reader` | `NOLOGIN` | `SELECT` on `reservation` |
| `reservations_writer` | `NOLOGIN` | `SELECT, INSERT, UPDATE` on `reservation` and `outbox_event`; `SELECT, INSERT` on `idempotency_key` and `processed_event`. **Never `DELETE`** (history is kept) and never DDL |
| `reservations_app` | `LOGIN`, created by `ftx-infra-postgres` | receives `reservations_writer`; `ftx-reservations-api` connects with it |

## How to run the migrations

From `ftx-infra-postgres`, with the repositories cloned as siblings:

```bash
docker network create platform                                            # once per machine
docker compose --env-file env/dev.env up -d --wait postgres               # the single instance
docker compose --env-file env/dev.env run --rm reservations-db-migrate    # apply what is pending
docker compose --env-file env/dev.env run --rm reservations-db-migrate    # again: "No migration necessary"
docker compose --env-file env/dev.env run --rm reservations-db-migrate info
```

`ftx-infra-postgres` must add `reservations_app` to its `postgres/init/01-instance.sh`,
`RESERVATIONS_APP_PASSWORD` to its env files and this file to its `include:` (Annex J.5.5).

## Rollback

Flyway Community does not revert. Each `V<n>` has its `U<n>` in `05_rollbacks/`, applied with
`psql` from the highest number to the lowest, after deleting
`reservations.flyway_schema_history` (Annex J.6). The CI does it on every Pull Request. In `qa`
and `main` a mistake is fixed with a **new** forward migration.

## Rules

- A migration that already ran in any environment is **never edited**: a fix is a new `V<n>`.
- The next migration takes the next number (`V013`), whatever its family.
- Every new `V<n>` comes with its `U<n>` and, if it adds a rule, a check in `tests/verify.sql`.
- In `qa` and `main`, never `docker compose down -v`: the volume is the history.

## Branching

`develop`, `qa` and `main` accept no direct commits. Per user story:
`hu-<id>-dev → develop`, then `git cherry-pick -x` into `hu-<id>-qa → qa`, then into a release
branch `→ main` with the instructor's approval and the tag `v3.0.0`.
